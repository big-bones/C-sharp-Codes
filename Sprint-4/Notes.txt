Security in API's:
Authentication : This is done to authenticate the user's identity
that is log in and then access things
You log in and create a JWT token
JWT is a signed information that has three parts there is a header describing the algorithm
that was used to hash the payload
Payload is just the claims or additional metadata about the entity or in this case user
It can include Role,Country etc.. that can be used later
The JWT is not encryption but signing it has three components Header,Payload and the signature
using the secret key that we define that is used to sign the token and provide the validation
we create a tokenHandler using class JwtSecurityHandler()
token descriptor has the array of claims
token is created using tokenHadler.CreateToken(tokenDescriptor)
we use Authorize attribute over a method or the controller to enforce the api that is being accessed
needs the user to be authenticated 
Authorize first checks the authentication and then checks the authorization using claims in JWT
token
Authorization : It is used to decide if the user has permissions to access particular endpoints
or resources 
User Identity is created after user is authenticated using Claims
Claim is metadata about the user that can include role,name,country..and other relevant properties
For authorization first the user needs to be authenticated using log in a JWT token with claims
is created and and roles and relevant polcies are assigned that can be checked on relevant
resources when we use [Authorize] attribute directly
[Authorize("Roles = Admin")] Role based authorization
Policy based autorization is based on some custom logic used 
Such as which country does a user belong to 
Is the age 18 or above etc...
Steps to create a Policy based authorization:
Create a class that takes in the input for the policy example country string that we want to allow
This class implements IAuthorizationRequirement(Name the class with Requirement ending)
This is also registered in services.AddAuthorization with the string of the required country
Create a class that is derived from AuthorizationHandler<CountryRequirement>
This has a method HandleRequirementAsync(Context,Requirement)
Do the required and use the attribute
[Authorize(Policy="CountryPolicy")]
CountryPolicy is the name used during registration

Content Negotiation : Determines the data type in which client and server communicate
A client asks for data in some specified format through Accept Header where they mention
acceptable formats to return data in 
Server to the best of it's capacity tries to honor this by serializing the data accordingly
If the server can not send the data in required format then it either sends in default format
or error is thrown
Server send a header called Content-Type to specify what is the type of content the data is
sent in
Useful because client and server can communicate with different data types and
we do not need to create a different resource end point to get different types of data
JSON is by default available and XML can be configured

------------------------------------------------------------------------------------------------
EF core tracks the object it does not have all the rows in it's memory
In the memory it tracks whatever was queried 
Entity can be in states like added,modified,unchanged,detached...etc
If a table has a primary key then it keeps track of PK in the memory
The line _context.Entry(category).State = EntityState.Modified
is creating a category object with PK = 1 and started tracking it directly
and when we say await _context.SaveChanges()
it basically means that we want to replace that category with PK = 1
with this category as well as start it's tracking
This is why it is fast that querying from the database and then modifying 
the individual elements one by one 
To track the entity that is already being tracked we have to query from the DB
using FindAsync() and then do the updates otherwise it does not work
The entities are tracked for the lifetime of DbContext in actual web application
DbContext is usually scoped which means for the lifetime/session of a particular user
we would keep tracking 
Navigation properties are resolved as and when asked(loading required)
Lazy loading : get the parent first and then just use . operator on that object(needs to be configured)
Eager loading : use .Include() and .ThenInclude()
Explicit loading : Load the parent entity first and then load related entities as and when required

Testing : 
Golas of Testing : 
Check if the functionality is working
Find errors early on that can reduce cost
Give a quality software as a deliverable
Types of Testing : 
Unit testing,integration testing,end to end testing,
acceptance testing : Done by end users
Performance and stress testing : Done under different conditions to check the load system can 
take stress testing is done in extreme conditions
Regression testing : Ensure new changes do not break the code
Smoke testing : Done right before sending to production
Unit testing:
This is done on the smallest program unit or methods
They are expected to be independent(without aid of other modules)
Should be easy to execute and fast and should cover most of the code
Integration testing is testing working of multiple units together
this is done to ensure if they work well together
Should be less than unit tests
Testing Pyramid : Says that you should write most number of unit tests followed by integration 
tests and then end to end tests because this balance helps to cover all levels and creates a
well tested software.
Bottom layer is unit tests in most numbers 
Followed by integration tests
Later end to end test to check the functionality of whole software
The layers from bottom to top is basically a reduction in number of test cases
TDD : Test driven development is a novel approach that says write tests first and then write
the code for functionality this basically says write a failing test(where the functionality
should fail) then write a basic code that should pass the functionality and then refactor 
the code to add to the functionality in similar process
AAA's of unit testing(Arrange => Act => Assert)
Arrange : For example create an object of the class where the functionality is that you want
to test and then create data that you want to use against the expected result
Act : Invoke the method that you want to test and get the result
Assert : Test against the expected value if the value matches and test passes
Fact : Represents a single test in Xunit and does not take input
defined using attribute over that method
Theory : Represents multiple tests that also can take input and test against that input
Assert.Throws<ExpectedException>(Action delegate) takes action delegate as input and
returns a expected exception object that needs to be passed inside the <>

SOLID principles : Solid principles are design principles that make the code more understandable,flexible
and maintainable code also needs to be reusable.
SRP:SRP says every class should have a single responsiblity this makes the code modular and easy to test
Open Closed Principles:Open for extension and closed for modification(entities not just classes)this is
for the reusability
Liskov Substitution Principle:It is an enforcement of Inheritance which is basically Is-A relationship
It ensures that subclass can stand in for it's superclass without breaking the code(It maintains integrity)
Interface Segregation Principle:No client should be forced to implement methods it does not use
Instead of large interface break down the interface into smaller interfaces and implement accordingly
Makes the code modular
Dependency Inversion Principle:High level modules should not depend on low level modules directly both 
should depend on abstraction(This decouples the system makes it more scalable)
Dependency Injection:This allows a class to recieve it's dependencies from external source rather 
than implementing itself it is implementation of Inversion of Control
Promotes decoupling makes system modular and easier to test,scale and maintain
IOC:Invert the control of object creation and management from the application code to a container or framework

Agile is a itreative software development methodlogy
It breaks down the project in small units called sprints
Each sprint is focused on creating working piece of software
It is customer centric because we have frequent releases and customer feedback to accomodate the changes
at any point the in the development unlike traditional development models like Waterfall model
Scrum is a framework of agile and so is Kanban Kanban can have a flexible sprint duration
User story and acceptance criteria
User Story: They are consice description of a feature from end user perspective 
usually written as
As a registered user I want to reset my password 
Acceptance criteria
These are criterias or requirement that a user story must have in order to become acceptable
It has functional and non functional requirements
Functional requirements are specific functions that must be present
Non functional requirements are secondary requirements like usability of the feature
Story points are assigned which is rough estimation of the work involved in the story
It is assigned collectively by team using methods like Planning poker
Points are assigned in Fibonaaci Series pattern higher the points the story is more complicated 
What are sprint ceremonies
Sprint Planning : Done on the first day of the sprint to decide what the team should achieve this sprint
User stories are created based on the backlog item taken from product backlog in the sprint backlog meet
Daily Scrum : Review of what was done yesterday and what is being done today
Sprint Review : This is demonstration of what was done during the sprint and gather feedback from stake holders(product owner)
Sprint Retrospective : It is a reflection on what good and what bad happend during the sprint and how can team improve 
Sprint Backlog : This meet involves choosing the backlog item from product backlog to be worked on in the next sprint
Product backlog is basically how many features will we have through the scope of the project
Sprint Velocity is a quantitative measure of work done by team through sprint depending on number of story points completed divided
by total story points created for the sprint
This is a good tool to access the performance of the team because we can change the number of story points for the next sprint
and plan and adjust next sprint accordingly
